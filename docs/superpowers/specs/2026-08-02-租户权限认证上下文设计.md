# 租户权限认证上下文设计

## 1. 目标与边界

本阶段为现有 FastAPI 退款接口增加数据库驱动的租户身份和权限校验，解决当前仅依赖开发 Header、未验证操作者是否属于租户的问题。

本阶段不实现 JWT、OAuth、SSO、密码登录或 Token 签发。`X-Tenant-Id`、`X-Actor-Id` 和 `X-Actor-Type` 仍作为本地开发身份输入，但 API 必须使用 PostgreSQL 中的 `User`、`Role`、`Permission` 和 `UserRole` 验证身份与权限。该方案是可测试的开发认证适配器，不等同于生产认证系统。

项目继续保持独立于 `E:\ai\EduAgent完整代码`，不共享其数据库、配置和认证模块。

## 2. 权限模型

现有身份模型已经包含：

- `User(tenant_id, status)`：租户内操作者；
- `Role(tenant_id, code, status)`：租户角色；
- `Permission(tenant_id, role_id, code, status)`：角色权限；
- `UserRole(tenant_id, user_id, role_id)`：用户与角色关联；
- `IdentityRepository.has_permission(scope, user_id, permission_code)`：租户范围内权限查询。

本阶段使用以下权限码：

| 接口 | 权限码 | 说明 |
| --- | --- | --- |
| `POST /api/v1/refunds` | `refund.request` | 提交退款申请 |
| `GET /api/v1/workflows/{thread_id}` | `refund.request` | 查询自己所属租户的退款工作流状态 |
| `POST /api/v1/approvals/{approval_request_id}` | `refund.approve` | 批准或拒绝高风险退款 |
| `GET /healthz` | 无 | 应用存活检查，不访问业务身份数据 |

当前不从 `X-Actor-Type` 推导权限。`X-Actor-Type` 只作为退款风险策略的输入，实际授权只由数据库中的有效用户和权限码决定。

## 3. 请求处理流程

```text
请求 Header
  → 解析 X-Tenant-Id / X-Actor-Id / X-Actor-Type
  → TenantScope
  → IdentityRepository.get_user_in_tenant
  → 校验 User.status == active
  → IdentityRepository.has_permission
  → 允许进入退款或审批路由
```

任何一步失败都不能进入退款服务或审批恢复服务：

- Header 缺失、UUID 非法：`400 invalid_tenant_context`；
- 用户不存在、用户不属于当前租户或用户非 active：`403 tenant_identity_invalid`；
- 用户属于当前租户但没有所需权限：`403 permission_denied`。

错误响应不暴露用户是否存在于其他租户，不返回角色列表、权限明细、SQL 或内部堆栈。

## 4. FastAPI 依赖边界

在 `backend/api/dependencies.py` 中增加参数化依赖：

```python
def require_permission(permission_code: str):
    async def dependency(
        context: RequestContext = Depends(get_request_context),
        session_factory: async_sessionmaker[AsyncSession] = Depends(get_session_factory_dependency),
    ) -> RequestContext:
        async with UnitOfWork(session_factory, scope=context.scope) as uow:
            user = await uow.identity.get_user_in_tenant(
                scope=context.scope,
                user_id=context.scope.actor_id,
            )
            if user is None or user.status != "active":
                raise HTTPException(status_code=403, detail={"code": "tenant_identity_invalid"})
            if not await uow.identity.has_permission(
                scope=context.scope,
                user_id=context.scope.actor_id,
                permission_code=permission_code,
            ):
                raise HTTPException(status_code=403, detail={"code": "permission_denied"})
        return context

    return dependency
```

依赖内部通过 `UnitOfWork(session_factory, scope=context.scope)` 查询当前用户和权限。路由只声明所需权限，不直接调用 IdentityRepository：

```python
context: RequestContext = Depends(require_permission("refund.request"))
```

这样可以保持 API 适配层、身份仓储和业务服务的职责分离，并允许后续将 Header 解析替换为 JWT 解析而不修改退款业务服务。

## 5. 安全不变量

1. 操作者必须属于 `TenantScope.tenant_id`，不能使用其他租户的用户 ID 绕过授权。
2. `User.status` 不是 `active` 时，任何退款和审批接口都返回 403。
3. 没有 `refund.request` 的用户不能提交退款，也不能查询退款 Workflow 状态。
4. 没有 `refund.approve` 的用户不能批准或拒绝审批。
5. 通过 Header 修改 `X-Actor-Type` 不能获得额外权限。
6. `healthz` 不触发身份数据库查询。
7. 通过权限校验后，原有退款幂等、跨租户、审批状态机和未知执行状态保护继续有效。

## 6. 测试策略

集成测试使用真实 PostgreSQL 创建临时租户、用户、角色、权限和用户角色关联，覆盖：

- 具备 `refund.request` 的 active 用户可以提交低风险退款；
- 缺少 `refund.request` 返回 403，数据库中没有新增退款；
- 具备 `refund.approve` 的用户可以处理高风险审批；
- 缺少 `refund.approve` 返回 403，审批仍为 `PENDING`；
- 其他租户用户 ID 与当前租户 Header 组合返回 403；
- inactive 用户返回 403；
- 已有 API、Agent、数据库测试继续通过。

## 7. 后续替换为生产认证

未来接入 JWT/OAuth 时，只替换身份输入适配器：由 Token 解析出 `tenant_id`、`user_id` 和 `actor_type`，再复用相同的 `require_permission`、IdentityRepository 和 TenantScope。生产认证的签名验证、Token 过期、撤销、密钥轮换和审计不在本阶段伪造实现。
