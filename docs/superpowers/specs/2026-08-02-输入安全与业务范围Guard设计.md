# 输入安全与业务范围 Guard 设计

## 1. 目标与边界

本阶段在 LangGraph 主图和退款业务工具之间增加两道确定性前置防线：输入安全 Guard 和业务范围 Guard。它们保护 HTTP API、内部调用以及未来 Worker 入口，确保恶意输入、越界问题和不明确请求不能直接进入支付、退款、审批或工单工具。

本阶段不接入 LLM 安全分类器、不新增 Redis、不实现正式身份认证、不调用外部支付平台。规则使用可审计的长度、关键词和正则匹配，并通过测试固定行为。

## 2. 推荐架构

```text
AgentState
  → InputSecurityGuard
  → DomainGuard
  → normalize_request
  → supervisor_agent
  → 专业 Agent 子图
  → policy_gate / 业务工具
```

输入安全 Guard 先执行；如果返回 `block` 或 `human_handoff`，主图立即结束，后续不进入 Supervisor、专业 Agent 和业务工具。Domain Guard 只在输入安全通过后运行，判断请求属于支持范围、需要澄清还是越界。

退款应用服务在调用业务工具前读取 Guard 结果：只有安全状态为 `allow` 且业务域为 `billing` 才能执行 `billing.preview` 和退款申请。这样即使未来某个内部入口绕过 HTTP，也不能绕过 Guard 直接产生退款副作用。

## 3. 结构化决策

新增不可变 Pydantic 模型：

```python
class GuardDecision(BaseModel):
    status: Literal["allow", "block", "human_handoff"]
    code: str
    reason: str


class DomainDecision(BaseModel):
    status: Literal["in_scope", "out_of_scope", "needs_clarification"]
    domain: Literal["billing", "account", "technical", "sla", "ticket", "knowledge", "customer_service"]
    reason: str
```

State 只保存 `status`、`code`、`domain` 和截断后的内部摘要，不保存命中的完整输入片段、系统 Prompt、密钥或银行卡号。

## 4. InputSecurityGuard

### 4.1 检测规则

规则码固定且可审计：

| 规则码 | 检测对象 | 结果 |
| --- | --- | --- |
| `input_too_long` | 超过 2000 个字符 | `block` |
| `prompt_injection` | `ignore previous instructions`、`忽略之前指令`、`system prompt`、要求泄露系统指令等 | `block` |
| `credential_exposure` | `sk-`、`Bearer`、`api_key=`、密码/密钥字段及银行卡号样式 | `block` |
| `unsafe_action_request` | 要求绕过审批、租户隔离或直接执行未授权工具 | `human_handoff` |

规则匹配采用大小写不敏感和 Unicode 归一化；对外只返回通用安全错误，不返回命中的关键词。输入为空由已有 `normalize_request` 处理为业务错误，Guard 不把空输入解释为安全通过。

### 4.2 决策规则

- 命中 `input_too_long`、`prompt_injection` 或 `credential_exposure`：`block`，不重试。
- 命中 `unsafe_action_request`：`human_handoff`，不调用工具。
- 未命中规则：`allow`。

## 5. DomainGuard

### 5.1 业务域

使用现有平台业务域：`billing`、`account`、`technical`、`sla`、`ticket`、`knowledge`、`customer_service`。

第一版规则：

- 退款、退费、扣费、账单、支付、发票、订阅：`billing`；
- 登录、密码、MFA、成员、权限、账户锁定：`account`；
- API、Webhook、同步、上传、服务不可用、性能：`technical`；
- SLA、支持等级、赔偿、紧急事件：`sla`；
- 工单、投诉、故障单、催办、转派：`ticket`；
- 知识、政策、SOP、如何使用：`knowledge`；
- 问候、一般说明、无法归类但不越界：`customer_service`。

### 5.2 决策规则

- 没有足够业务关键词但可以通过一个问题澄清：`needs_clarification`，下一动作 `ask_clarification`。
- 明确要求真实生产资金、真实凭据或不属于 CloudDesk 支持范围：`out_of_scope`，不调用业务工具。
- 属于已支持业务域：`in_scope`，交给 Supervisor 路由。

退款应用服务要求 `domain == billing`。如果外部请求使用退款接口但消息明显属于其他业务域，服务记录 `domain_out_of_scope` 并结束，不读取 Payment，不创建 Refund。

## 6. LangGraph 与服务接入

主图新增节点：

- `input_security_guard`：读取最后一条用户消息，写入 `guard_decision`；
- `domain_guard`：读取安全通过的消息，写入 `domain_decision`。

条件边：

```text
input_security_guard
  ├─ block / human_handoff → END
  └─ allow → domain_guard

domain_guard
  ├─ out_of_scope / needs_clarification → END
  └─ in_scope → normalize_request → supervisor_agent
```

`RefundWorkflowService` 在保存 RuntimeTrace 后调用主图；Guard 终止结果必须：

1. 写入同一租户的 `AuditLog`，动作分别为 `input_security_blocked`、`domain_out_of_scope` 或 `domain_clarification_required`；
2. 完成 `RuntimeTrace`，状态分别为 `blocked`、`out_of_scope` 或 `needs_clarification`；
3. 保存不含敏感原文的 `WorkflowCheckpoint`，保留 thread、trace 和原退款幂等键；
4. 返回结构化 `WorkflowResult`，不创建 Refund、不创建 ApprovalRequest、不记录 billing 工具执行。

## 7. 错误和降级

Guard 决策不是异常，不进入通用重试。HTTP 层将其映射为业务响应：

| Guard 结果 | Workflow 状态 | HTTP 结果 |
| --- | --- | --- |
| `block` | `blocked` | `422 security_blocked` |
| `human_handoff` | `human_handoff` | `202` |
| `out_of_scope` | `out_of_scope` | `422 out_of_scope` |
| `needs_clarification` | `needs_clarification` | `200`，返回澄清下一动作 |

响应只包含 request_id、thread_id、状态、通用 reason 和 next_action，不返回规则码对应的敏感匹配内容。

## 8. 测试策略

### 单元测试

- Prompt Injection 中文/英文变体被 block；
- API Key、Bearer、银行卡号等敏感输入被 block；
- 绕过审批请求进入 human handoff；
- 普通退款、账单、工单、知识请求被正确分类；
- 模糊输入需要澄清；
- 规则匹配不把原始敏感片段写入决策摘要。

### 集成测试

- 恶意退款消息不产生 Refund、ApprovalRequest 或 billing ToolExecution；
- 非 billing 消息通过退款应用服务时不读取 Payment；
- Guard 阻断和越界结果写入同一租户 AuditLog、RuntimeTrace、WorkflowCheckpoint；
- 正常退款链路、RBAC、幂等和审批恢复继续通过；
- API 返回不泄露检测关键词和输入原文。

## 9. 后续阶段

本阶段完成后，才能安全地接入真实 LangChain 模型调用、知识检索和异步 Worker。后续模型输出仍必须经过同一套确定性 Guard、权限、策略和工具白名单，不能用模型替代这些边界。
