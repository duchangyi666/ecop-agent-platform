# 退款业务 HTTP API 设计

## 1. 目标与边界

本阶段把已经通过 PostgreSQL、LangGraph、退款幂等和审批恢复验收的领域能力接入 FastAPI，形成一个可通过 HTTP 调用、可测试、可审计的退款业务入口。

本阶段只实现退款垂直链路的 API，不同时引入前端、正式身份认证、异步 Worker、Redis、SSE 事件总线或外部支付网关。API 返回“本地退款申请和审批状态”，不代表第三方资金已经到账。

项目完全独立于 `E:\ai\EduAgent完整代码`。当前实际环境版本以 `E:\anaconda3\envs\edu_agent` 为准：Python 3.11.15、FastAPI 0.117.1、Uvicorn 0.32.1、HTTPX 0.28.1、SSE-Starlette 2.1.3。

## 2. 设计方案

### 2.1 推荐方案：模块化 FastAPI 入口

新增 `backend/api` 作为 HTTP 适配层，新增 `backend/main.py` 作为应用入口。API 层只负责请求解析、开发环境租户上下文、响应映射和异常转换；退款业务仍由现有 `RefundWorkflowService` 与 `resume_refund_after_approval` 执行。

调用链如下：

```text
HTTP 请求
  → FastAPI 路由
  → HeaderTenantContext
  → Pydantic 请求模型
  → RefundWorkflowRequest / TenantScope
  → RefundWorkflowService 或审批恢复服务
  → UnitOfWork + PostgreSQL Repository
  → 脱敏响应
```

### 2.2 不采用的方案

- 直接在路由中写 SQL：会绕过现有 Repository、Unit of Work 和租户过滤。
- 在本阶段接入 JWT、OAuth 或真实 SSO：当前项目还没有身份提供方和密钥管理边界，先保留显式开发上下文适配器。
- 在本阶段接入 SSE：当前没有事件表或事件发布器，先提供可轮询的 Checkpoint 查询，后续独立增加事件流。
- 在本阶段启动后台 Worker：退款服务当前是可验证的同步数据库事务，长任务队列应作为独立子项目设计。

## 3. API 合同

### 3.1 开发环境租户上下文

所有业务接口要求以下请求头：

| Header | 类型 | 说明 |
| --- | --- | --- |
| `X-Tenant-Id` | UUID | 当前租户 ID |
| `X-Actor-Id` | UUID | 当前操作者用户 ID |
| `X-Actor-Type` | 字符串 | `user`、`service` 等策略使用的操作者类型 |
| `X-Request-Id` | 字符串，可选 | 外部请求关联号；缺省由 API 生成 |

缺少必需 Header、UUID 格式错误或 `X-Actor-Type` 为空时返回 `400 invalid_tenant_context`。本适配器名称和文档明确标注为开发环境上下文，不能被解释为生产认证。

### 3.2 提交退款

`POST /api/v1/refunds`

请求体：

```json
{
  "thread_id": "thread-refund-001",
  "payment_id": "00000000-0000-0000-0000-000000000001",
  "amount": "20.00",
  "refund_idempotency_key": "refund-tenant-a-001",
  "message": "重复扣费申请退款"
}
```

处理规则：

1. API 使用 Header 构造 `TenantScope`，不能从请求体接收或覆盖租户 ID。
2. API 构造 `AgentState` 和 `RefundWorkflowRequest`，调用现有数据库退款服务。
3. 低风险结果返回 `200` 与 `status=refund_requested`。
4. 高风险结果返回 `202` 与 `status=awaiting_approval`、`approval_request_id`。
5. 业务拒绝返回 `422`，包括金额非法、支付不可见、未知执行状态等情况。
6. 同一租户、同一幂等键复用已有 `Refund`，不会创建第二条退款。

响应示例：

```json
{
  "request_id": "request-001",
  "thread_id": "thread-refund-001",
  "status": "awaiting_approval",
  "refund_id": "00000000-0000-0000-0000-000000000002",
  "approval_request_id": "00000000-0000-0000-0000-000000000003",
  "trace_id": "00000000-0000-0000-0000-000000000004",
  "next_action": "human_handoff"
}
```

### 3.3 处理审批

`POST /api/v1/approvals/{approval_request_id}`

请求体：

```json
{
  "thread_id": "thread-refund-001",
  "approved": false,
  "reason": "重复扣费证据不足"
}
```

处理规则：

- 通过 Header 租户范围读取 `ApprovalRequest` 和 `WorkflowCheckpoint`。
- 只允许 `PENDING` 审批处理；已批准、已拒绝或其他终态返回 `409 approval_not_pending`。
- `approved=true` 返回 `200`、`status=approved_for_execution`，但不声称第三方退款已完成。
- `approved=false` 返回 `200`、`status=rejected`，不会创建第二条退款。
- 审批理由只保存脱敏摘要，不把完整请求或敏感字段写入响应。

### 3.4 查询工作流状态

`GET /api/v1/workflows/{thread_id}`

处理规则：

- 只返回当前租户可见的 `WorkflowCheckpoint`。
- 返回 `thread_id`、状态、下一动作、退款幂等键是否存在、退款 ID、审批 ID 和 trace ID。
- 不返回完整 LangGraph State、系统 Prompt、模型原始输出、工具敏感参数或完整审计内容。
- 不存在时返回 `404 workflow_not_found`。

响应示例：

```json
{
  "thread_id": "thread-refund-001",
  "status": "awaiting_approval",
  "next_action": "human_handoff",
  "refund_id": "00000000-0000-0000-0000-000000000002",
  "approval_request_id": "00000000-0000-0000-0000-000000000003",
  "trace_id": "00000000-0000-0000-0000-000000000004",
  "has_refund_idempotency_key": true
}
```

### 3.5 健康检查

`GET /healthz`

只返回应用存活信息，不访问业务数据，不泄露数据库连接串、依赖凭据或内部 Trace。

## 4. 错误合同

统一错误结构：

```json
{
  "error": {
    "code": "invalid_tenant_context",
    "message": "tenant context is required",
    "request_id": "request-001"
  }
}
```

错误映射：

| HTTP 状态 | 错误码 | 来源 |
| --- | --- | --- |
| 400 | `invalid_request` | JSON、UUID、金额或 Header 格式错误 |
| 400 | `invalid_tenant_context` | 租户上下文缺失或非法 |
| 404 | `workflow_not_found` | 当前租户没有该 thread Checkpoint |
| 409 | `approval_not_pending` | 审批已处理，不能重复处理 |
| 422 | `business_rule_rejected` | 金额、支付状态、未知执行状态或租户业务约束 |
| 500 | `internal_error` | 未预期错误，仅记录内部日志摘要 |

响应中的错误消息不包含 SQL、完整异常堆栈、密钥、Prompt 或敏感业务 payload。

## 5. 文件边界

| 文件 | 职责 |
| --- | --- |
| `backend/main.py` | 创建 FastAPI 应用、注册路由、健康检查、异常处理 |
| `backend/api/dependencies.py` | 解析开发环境租户 Header 和请求关联号 |
| `backend/api/schemas.py` | 请求、响应和统一错误 Pydantic 模型 |
| `backend/api/routes/refunds.py` | 退款提交与工作流状态查询 |
| `backend/api/routes/approvals.py` | 审批批准/拒绝接口 |
| `tests/unit/api` | Header、Schema、异常映射和脱敏测试 |
| `tests/integration/api` | 使用真实 PostgreSQL 验收 HTTP 到数据库闭环 |

API 层不修改 `backend/database` 的租户过滤规则，不复制退款策略，不直接调用外部支付平台。

## 6. 测试验收

必须覆盖：

1. 健康检查不访问业务数据。
2. 缺少租户 Header 被拒绝。
3. 合法低风险请求返回 `refund_requested`。
4. 高风险请求返回 `awaiting_approval` 和审批号。
5. 审批批准、拒绝和重复审批的状态码与状态正确。
6. 同一租户同一幂等键不会创建第二条退款。
7. 跨租户不能读取支付、审批或 Checkpoint。
8. 状态查询不泄露完整 State 和敏感字段。
9. 当前实际 Python/依赖环境下 `pip check`、编译、Alembic 和现有 135 项测试继续通过。

## 7. 后续独立阶段

以下内容不在本阶段实现：正式 JWT/OAuth 认证、SSE 事件流、Redis/Worker、前端控制台、知识库 RAG、Mock 外部服务和生产部署。每项都应在现有 HTTP API 骨架稳定后单独设计和验收。
