# Agent 最终工作流设计

## 1. 目标

为企业级客户运营平台设计一套可长期扩展的单一 Agent 工作流。最终架构只有一张业务流程图和一个客服运营主 Agent，但允许接入多个确定性业务节点、业务工具、人工审批节点、Checkpoint、审计和运行追踪。

第一条落地业务链为“退款/计费异常处理”，后续知识问答、支付查询、工单分类和客户信息维护都通过相同的 State、Node Contract 和 Tool Contract 扩展，不重构主流程。

## 2. 范围与非目标

### 本阶段范围

- 统一请求入口和 `AgentState`。
- 主 Agent 的结构化意图判断与动作选择。
- 知识检索、支付查询、退款预检查、退款执行和工单写入节点。
- 风险策略和人工审批分支。
- Unit of Work 事务边界、Checkpoint、审计事件和运行追踪。
- 失败重试、降级回复和人工接管。

### 本阶段不做

- 不拆分客服 Agent、计费 Agent、工单 Agent 等多个自治 Agent。
- 不引入 Supervisor、Agent 间自由对话和无边界的自主循环。
- 不把消息队列、分布式任务调度和多区域部署作为第一条业务链的前置条件。
- 不把模型输出直接当作支付、退款、权限或审批结论。

## 3. 总体架构

```text
请求接入
  ↓
请求标准化与租户作用域校验
  ↓
AgentState 初始化 / 恢复 Checkpoint
  ↓
客服运营主 Agent：识别意图、选择允许的下一动作
  ↓
确定性路由
  ├─ 知识问答：检索 → 证据整理 → 回复
  ├─ 退款/计费：支付查询 → 风险策略 → 审批或执行
  ├─ 工单处理：查询工单 → 状态转换 → 事件与审计
  └─ 信息不足：追问或创建工单
  ↓
结果校验与回复生成
  ↓
审计事件、运行追踪、Checkpoint 持久化
  ↓
返回客服回复 / 审批中 / 工单处理中
```

LangGraph 只负责节点编排、条件边和状态传递；业务规则由领域函数、Repository 和策略服务负责。主 Agent 的每个动作必须映射到已注册工具或确定性节点，不能生成任意 Python 调用。

## 4. AgentState

`AgentState` 是工作流唯一共享状态，所有节点只读取自己需要的字段并返回增量更新。建议字段如下：

| 字段 | 类型 | 责任 |
| --- | --- | --- |
| `request_id` | `UUID` | 一次客户请求的稳定标识 |
| `tenant_scope` | `TenantScope` | 租户、操作者和操作者类型 |
| `customer_id` | `UUID \| None` | 当前客户 |
| `conversation` | `list[Message]` | 脱敏后的对话消息 |
| `intent` | `IntentDecision \| None` | 主 Agent 的结构化意图和置信度 |
| `retrieval_context` | `list[Evidence]` | 可引用的知识证据，不保存原始敏感内容 |
| `tool_calls` | `list[ToolCallRecord]` | 工具调用计划、状态和摘要 |
| `approval` | `ApprovalState` | 是否需要审批、审批请求和当前状态 |
| `ticket_id` | `UUID \| None` | 关联工单 |
| `response_draft` | `str \| None` | 待校验客服回复 |
| `final_response` | `str \| None` | 可返回给客户的回复 |
| `errors` | `list[WorkflowError]` | 可重试错误和业务错误摘要 |
| `audit_event_ids` | `list[UUID]` | 已写入审计事件 |
| `trace_id` | `UUID` | RuntimeTrace 关联标识 |
| `next_action` | `NextAction` | 受控的下一动作枚举 |

State 不保存 API Key、银行卡号、原始系统 Prompt、完整工具密钥参数或未经脱敏的客户隐私字段。Checkpoint 与 RuntimeTrace 只保存摘要、哈希和必要的恢复字段。

## 5. 节点与职责

| 节点 | 类型 | 输入 | 输出 |
| --- | --- | --- | --- |
| `normalize_request` | 确定性 | 入口请求、认证上下文 | 标准化消息、`TenantScope`、`request_id` |
| `load_checkpoint` | 确定性 | `request_id` | 恢复后的 State 或新 State |
| `intent_agent` | 主 Agent 模型调用 | 对话、客户摘要、允许能力 | `IntentDecision`、`next_action` |
| `retrieve_context` | 检索节点 | 意图、租户、查询文本 | `Evidence` 列表 |
| `load_billing_context` | Repository 节点 | 客户、支付/发票标识、租户作用域 | 脱敏账单摘要 |
| `evaluate_risk` | 确定性策略 | 金额、动作、角色、历史状态 | 风险等级、是否审批 |
| `request_approval` | Repository 节点 | 审批动作、payload 摘要、租户作用域 | `ApprovalRequest`、等待状态 |
| `execute_billing_tool` | 受控工具节点 | 已审批动作、幂等键、租户作用域 | 工具结果摘要、支付/退款状态 |
| `create_or_update_ticket` | Repository 节点 | 客户、主题、状态转换、租户作用域 | `ticket_id`、事件和审计 ID |
| `generate_response` | 主 Agent 模型调用 | 业务结果、证据、审批/工单状态 | 回复草稿 |
| `validate_response` | 确定性 | 回复草稿、动作结果 | 可发送回复或降级原因 |
| `persist_trace_and_checkpoint` | 持久化节点 | State 摘要、节点结果 | Trace、Span、Checkpoint |

主 Agent 只在 `intent_agent` 和 `generate_response` 两处调用模型。`evaluate_risk`、审批条件、金额比较、状态转换和工具参数校验由代码完成。

## 6. Node Contract

节点不直接修改共享 State，而返回结构化增量：

```python
class NodeResult(TypedDict, total=False):
    state_updates: dict[str, object]
    next_action: str
    events: list[dict[str, object]]
    retryable: bool
    error_code: str
    error_summary: str
```

节点必须满足：

- 输入字段明确，缺失关键字段时返回业务错误，不隐式猜测。
- 输出只能写入允许的 State 字段。
- 读写业务数据必须携带 `TenantScope`。
- 外部工具调用必须包含幂等键、超时和结果摘要。
- 节点失败必须区分可重试错误、需要审批、需要追问和人工接管。

## 7. Tool Contract

所有业务工具通过注册表暴露，主 Agent 只能选择注册工具：

```python
class ToolContract(Protocol):
    name: str
    risk_level: str
    requires_approval: bool

    async def preview(self, request: ToolRequest) -> ToolPreview: ...
    async def execute(self, request: ToolRequest) -> ToolResult: ...
```

退款工具必须分为 `preview` 和 `execute`：

1. `preview` 查询支付、校验金额、生成幂等键和风险摘要。
2. `evaluate_risk` 决定自动执行或申请审批。
3. `execute` 只接受审批通过或低风险动作，并在同一 Unit of Work 中写入退款与审计。

工具返回业务结果，不把第三方 SDK 原始响应直接放入 State 或客户回复。

## 8. 条件路由与人工审批

`next_action` 使用受控枚举：`answer_with_knowledge`、`load_billing`、`request_approval`、`execute_tool`、`create_ticket`、`ask_clarification`、`human_handoff`、`finish`。

退款路由规则：

- 支付不存在或不属于当前租户：返回业务失败，不暴露跨租户数据。
- 金额超过支付金额：拒绝执行并说明原因。
- 未知执行状态未对账：禁止再次执行，创建人工处理工单。
- 低风险且权限满足：进入执行节点。
- 高风险、权限不足或策略不确定：创建审批请求，工作流暂停并保存 Checkpoint。
- 审批拒绝：生成拒绝回复并写入工单/审计。
- 审批通过：使用原幂等键恢复执行，不重新生成另一条业务动作。

## 9. 事务、Checkpoint 与一致性

每次业务写入使用现有 `UnitOfWork`：

- 退款申请、审批动作、工单事件和审计记录必须在明确的事务边界内写入。
- 正常节点链提交；异常节点回滚。
- 外部支付工具调用不与数据库长事务绑定；执行前写入意图和幂等键，执行后以结果状态更新。
- 审批等待前保存 Checkpoint，恢复时重新读取数据库状态，不只相信旧 State。
- Checkpoint 只保存脱敏摘要、状态版本和恢复所需的业务 ID。

第一版可以先实现 PostgreSQL Checkpoint 接口和可测试的内存实现；生产实现必须落到独立的 Checkpoint 存储，不与业务表的状态字段混用。

## 10. 错误、重试与降级

- 模型超时、临时网络错误和限流错误：按有限次数重试，超过上限转人工接管或创建工单。
- 参数校验、权限不足、金额不合法和状态非法：不重试，返回业务结果。
- 工具结果未知：不自动补偿式重试，进入对账/人工流程。
- 回复生成失败：返回固定的处理中提示，并保留 `request_id`、工单号或审批号。
- 任一异常都写入错误摘要、节点名称、Trace 和审计事件，禁止保存敏感原文。

## 11. 租户、安全和可观测性

- 入口从认证上下文建立不可变 `TenantScope`，节点不得从客户输入覆盖租户 ID。
- Repository 查询必须带租户过滤和软删除过滤。
- 工具注册表保存工具名称、风险等级、输入 schema 和权限要求。
- RuntimeTrace、RuntimeSpan 和 ToolExecution 记录节点耗时、重试次数、模型摘要、成本和结果摘要。
- 审计事件记录操作者、租户、动作、状态变化和关联请求 ID。

## 12. 测试策略

- State 测试：缺字段、状态合并、Checkpoint 恢复和敏感字段脱敏。
- Agent 输出测试：结构化意图、无效动作拒绝和低置信度转人工。
- 路由测试：低风险自动执行、高风险审批、未知状态对账、信息不足追问。
- 工具测试：preview/execute 分离、幂等键、租户边界和参数校验。
- 集成测试：退款申请、审批恢复、工单事件、审计记录在同一事务内一致。
- 回归测试：跨租户读取、数据库迁移、`alembic check` 和 Phase 2 全量测试持续通过。

## 13. 分阶段实现顺序

1. 冻结 State、Node Contract、Tool Contract 和路由枚举。
2. 实现工作流骨架、状态合并和测试用 Checkpoint。
3. 接入主 Agent 的结构化意图判断与回复生成。
4. 接入退款 preview、风险策略、审批等待和 execute 恢复。
5. 接入工单、审计、RuntimeTrace 和错误降级。
6. 用真实 PostgreSQL 完成退款、审批恢复、跨租户和迁移回归验收。

完成上述接口后，新增业务能力只需要增加节点、工具和路由分支，不改变主 State 和事务入口。
