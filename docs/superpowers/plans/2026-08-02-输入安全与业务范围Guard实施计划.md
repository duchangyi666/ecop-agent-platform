# 输入安全与业务范围 Guard 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在 LangGraph 主图和退款应用服务前增加可审计的输入安全 Guard 与业务范围 Guard，使恶意输入、越界请求和需要澄清的请求不会进入支付、退款、审批或其他业务工具，同时保留正常退款、权限、幂等和审批恢复链路。

**Architecture:** 使用纯 Python/Pydantic 的确定性规则实现两个 Guard；主图顺序固定为 \`input_security_guard -> domain_guard -> normalize_request -> supervisor_agent\`。Guard 终止结果通过 AgentState 传给 \`RefundWorkflowService\`，由服务统一写入同一租户的 AuditLog、RuntimeTrace 和 WorkflowCheckpoint，再决定是否允许创建退款业务副作用。第一版不引入 LLM 分类器、Redis、正式身份认证或外部支付调用。

**Tech Stack:** Python 3.11.15、Pydantic 2.11.4、LangGraph 1.0.9、FastAPI 0.117.1、SQLAlchemy 2.0.36、pytest 8.3.4、pytest-asyncio 0.24.0。

## 全局约束

- 所有文档文件使用中文文件名；保持当前项目与现有项目完全独立。
- Guard 决策不是异常，不进入通用重试；规则只保存通用原因和截断摘要，不保存命中的敏感原文、系统 Prompt、密钥或银行卡号。
- HTTP 入口仍先执行现有租户上下文和 RBAC；Guard 只负责输入安全与业务范围，不替代身份和权限校验。
- 退款应用服务必须在读取 Payment、创建 Refund、创建 ApprovalRequest 或记录 \`billing\` 工具执行前检查 Guard 结果和 \`billing\` 业务域。
- 不修改现有数据库迁移结构，优先复用现有 AuditLog、RuntimeTrace、WorkflowCheckpoint、Refund 和 ApprovalRequest 仓储。
- 每个任务先写失败测试，再写最小实现；每个任务完成后运行对应测试并提交一个小步提交。

**Files:**

### Step 1: 写失败的单元测试

覆盖以下可观察行为：

- 英文和中文 Prompt Injection 返回 \`block/prompt_injection\`；
- 超过 2000 个字符返回 \`block/input_too_long\`；
- \`sk-\`、Bearer、\`api_key=\`、密码字段和银行卡号样式返回 \`block/credential_exposure\`；
- 绕过审批、租户隔离或未授权工具的请求返回 \`human_handoff/unsafe_action_request\`；
- 普通退款输入返回 \`allow\`，且决策不包含输入原文；
- 退款、账户、技术、SLA、工单、知识请求分类为 \`in_scope\`；
- 模糊输入分类为 \`needs_clarification\`，明确真实生产资金或 CloudDesk 范围外请求分类为 \`out_of_scope\`；
- 决策对象只暴露固定状态、规则码、业务域和通用原因，不回显命中的完整片段。

### Step 2: 实现最小 Guard 接口

在 \`backend/agent/guards.py\` 中实现：

- 冻结的 \`GuardDecision\`：\`status\` 为 \`allow/block/human_handoff\`，包含 \`code\`、通用 \`reason\`；
- 冻结的 \`DomainDecision\`：\`status\` 为 \`in_scope/out_of_scope/needs_clarification\`，包含固定 \`domain\`、通用 \`reason\`；
- \`InputSecurityGuard.evaluate(text)\`：Unicode 归一化、大小写不敏感匹配，按长度、注入、凭据、危险动作顺序返回首个可审计结果；
- \`DomainGuard.evaluate(text)\`：按固定业务域关键词分类；支持范围外和需要澄清优先于默认客户服务；
- 内部摘要只允许固定短文本，禁止拼接原始命中内容。

在 \`AgentState\` 中增加可选的 \`guard_decision\`、\`domain_decision\` 字段，使 LangGraph 可以保存结构化决策。

## 任务 2：把 Guard 接入 LangGraph 主图

### Step 1: 写失败的图执行测试

使用现有主图的异步调用验证：

- 恶意输入在 \`input_security_guard\` 终止，\`supervisor_decision\` 和专业 Agent 结果为空；
- 危险动作请求返回 \`human_handoff\` 并终止；
- 非退款业务输入在 \`domain_guard\` 终止为越界或澄清；
- 普通退款输入依次经过两个 Guard、normalize 和 Supervisor，并仍得到 \`route_billing\`；
- 空输入仍由既有 normalize 逻辑负责，不能被 Guard 错误当成正常业务。

~~~powershell

~~~

预期：因节点和路由尚未注册而失败。

### Step 2: 实现 Guard 节点和条件路由

在 \`backend/agent/nodes/guards.py\` 中实现：

- \`input_security_guard_node(state)\`：读取最后一条用户消息，调用 \`InputSecurityGuard\`，写入 \`guard_decision\`；
- \`domain_guard_node(state)\`：仅对安全通过的输入调用 \`DomainGuard\`，写入 \`domain_decision\`；
- \`route_after_input_security(state)\`：\`allow\` 路由至 \`domain_guard\`，其他状态路由 \`END\`；
- \`route_after_domain(state)\`：\`in_scope\` 路由至 \`normalize_request\`，其他状态路由 \`END\`。

在 \`main_graph.py\` 中把两个 Guard 注册为入口前置节点，并保持现有专业 Agent 路由不变。图层只负责决策和终止，不在节点中写数据库或调用业务工具。

### Step 1: 写失败的服务和 API 集成测试

测试必须通过现有租户和 RBAC fixture：

- 已授权用户提交包含 Prompt Injection 或凭据的退款消息，HTTP 返回 422 \`security_blocked\`；数据库中没有 Refund、ApprovalRequest 或 \`billing\` ToolExecution；
- 已授权用户通过退款接口提交账户、技术或知识问题，返回 422 \`out_of_scope\`，且不读取 Payment；
- 模糊消息返回 200 \`needs_clarification\` 和 \`ask_clarification\`；
- 绕过审批等危险动作返回 202 \`human_handoff\`；
- Guard 结果在同一租户写入正确 AuditLog action、RuntimeTrace status 和 WorkflowCheckpoint；
- 正常退款仍完成既有 preview、策略和幂等逻辑；
- 现有权限拒绝仍在 Guard 之前返回 403；
- 仅有 \`refund.request\` 权限的审批请求使用包含“退款”业务词的消息，仍能到达审批权限拒绝分支，避免测试输入被业务范围 Guard 提前截断；
- API 响应不返回输入原文、密钥、银行卡号或命中规则的完整关键词。

### Step 2: 实现服务层治理终止

在 \`RefundWorkflowService\` 中：

- 在 RuntimeTrace 创建后调用主图并读取 \`guard_decision\`、\`domain_decision\`；
- 对 Guard 终止结果统一生成不含敏感原文的 \`WorkflowResult\` 状态；
- 使用现有仓储写入同一租户 AuditLog：\`input_security_blocked\`、\`domain_out_of_scope\`、\`domain_clarification_required\`；
- 完成 RuntimeTrace，状态映射为 \`blocked\`、\`out_of_scope\`、\`needs_clarification\`；危险动作使用 \`human_handoff\` 结果并标记为人工接管；
- 保存 WorkflowCheckpoint，保留 thread、trace、幂等键和安全摘要；
- 在任何 Guard 终止分支返回前，不读取 Payment，不创建 Refund、ApprovalRequest，不记录 billing 工具执行；
- 只有 \`guard_decision.status == allow\` 且 \`domain_decision.status == in_scope\` 且业务域为 \`billing\` 时，才进入现有退款 preview 和策略流程。

### Step 3: 实现 API 响应映射

在响应模型增加可选 \`reason\` 和 \`next_action\`（保持已有字段兼容），在退款路由中按工作流状态映射：

- \`blocked/out_of_scope\`：HTTP 422，错误码分别为 \`security_blocked/out_of_scope\`；
- \`human_handoff\`：HTTP 202；
- \`needs_clarification\`：HTTP 200，返回 \`next_action=ask_clarification\`；
- 既有审批等待和已完成状态保持原有行为。

统一错误信息使用通用文案，不暴露 Guard 的匹配细节。
